# Project Context

This document captures the current understanding of the repo as of 2026-04-28.

## What This Project Is

This is a Next.js 16 App Router application for stress-testing a protected admin API.

The main user workflow is:

1. Pass a lightweight OTP gate.
2. Provide API credentials manually or capture an already-encrypted password from a real login page.
3. Repeatedly hit an upstream `/admin/dashboard` endpoint with configurable concurrency and timing.
4. Watch live stats and export client-side execution logs.

At a product level, this is closer to an internal operations tool than a public SaaS app.

## High-Level Flow

1. The user opens `/` and is blocked by `AuthGate`.
2. `AuthGate` requests an OTP and verifies it through `/api/auth/request-otp` and `/api/auth/verify-otp`.
3. On success, a JWT is stored in `localStorage` under `auth_token`.
4. The main dashboard lets the user choose one of two credential paths:
   - Manual path: enter `base_url`, `username`, and `password`, then use "Test Credentials".
   - Capture path: launch Puppeteer against a real frontend login page, intercept the outgoing `/admin/login` request, and reuse the encrypted password that the frontend already produced.
5. When the test starts, the runner waits until `start_time` if needed, then repeatedly sends batches of requests until `end_time` or manual stop.
6. All upstream traffic is routed through a local Next.js proxy endpoint to avoid browser CORS issues.

## Architecture Overview

### Frontend

- `app/page.tsx`
  The main client page. It wires together the form, status panel, controls, capture panel, and OTP gate.
- `app/components/Form.tsx`
  Collects `base_url`, `username`, `password`, concurrency, interval, and execution window.
- `app/components/CapturePanel.tsx`
  Starts capture mode and shows intercepted payload/debug logs.
- `app/components/StatusPanel.tsx`
  Displays totals, success rate, last response, and execution logs.
- `app/components/Controls.tsx`
  Handles test, run, stop, and log export actions.
- `app/components/AuthGate.tsx`
  Presents the OTP UI and stores the returned JWT in `localStorage`.
- `app/hooks/useRunner.ts`
  Owns the timed batch runner, logging, stop behavior, and elapsed timer.
- `app/utils/api.ts`
  Wraps the manual login and dashboard requests.
- `app/utils/encrypt.ts`
  AES-encrypts plaintext passwords in the browser using `NEXT_PUBLIC_CRYPTO_SECRET_KEY`.

### Server Routes

- `app/api/proxy/route.ts`
  Generic server-side proxy. The client posts a target URL plus method/body/params, and the server forwards that request upstream.
- `app/api/capture-login/route.ts`
  Launches Puppeteer, navigates to a login page, fills in credentials, clicks submit, intercepts `POST /admin/login`, and extracts the encrypted password and base URL.
- `app/api/auth/request-otp/route.ts`
  Generates an OTP, hashes it, stores it in cache, rate-limits requests per IP, and sends OTP emails.
- `app/api/auth/verify-otp/route.ts`
  Verifies the OTP, creates a session id, signs a JWT, and sends audit email on success/failure.

### Auth Utilities

- `lib/auth/cache.ts`
  In-memory TTL caches for OTPs, active sessions, and rate limiting.
- `lib/auth/otp.service.ts`
  Generates, hashes, stores, and verifies OTPs.
- `lib/auth/email.service.ts`
  Sends OTP and audit emails via SMTP.
- `lib/auth/metadata.util.ts`
  Extracts IP, browser, OS, and device info from the request headers.

### App Shell / Styling

- `app/layout.tsx`
  Root layout with metadata, Google Fonts, and Emotion integration.
- `app/EmotionRegistry.tsx`
  Handles Emotion style injection for the App Router setup.
- `app/theme.ts`
  Defines the dark MUI theme used across the UI.

## Core Runtime Behavior

### Credential Modes

- Manual mode:
  The browser AES-encrypts the plaintext password, then `/api/proxy` forwards a `POST` to `https://<base_url>/admin/login`.
- Capture mode:
  Puppeteer intercepts the encrypted password already generated by the target frontend. That captured value is then reused directly and bypasses local re-encryption.

### Stress Runner

- The runner is client-side.
- It caps concurrency at 20 in `useRunner`.
- The form UI clamps interval to a minimum of 500ms.
- Each batch fires `concurrency` parallel requests to the upstream dashboard.
- Between batches, the runner waits `concurrency_interval` milliseconds.
- The loop ends when:
  - the current time passes `end_time`, or
  - the user presses stop, or
  - the request signal is aborted.
- Logs are kept client-side and trimmed to the latest 500 entries.
- Export downloads the logs as JSON.

### Upstream Contract Assumptions

The app assumes an upstream backend with endpoints shaped like:

- `https://<base_url>/admin/login`
- `https://<base_url>/admin/dashboard`

It also assumes:

- login accepts a `user` field and an AES-encrypted `password`
- the frontend login page eventually makes a `POST` request to `/admin/login`
- the dashboard endpoint accepts `user` and `password` as query params

## Environment Variables

These are the environment variables currently used by the codebase:

- `NEXT_PUBLIC_CRYPTO_SECRET_KEY`
  Used by `app/utils/encrypt.ts`. Required for browser-side AES encryption. Because it is `NEXT_PUBLIC_*`, it is exposed to the client bundle.
- `JWT_SECRET`
  Used when signing the OTP JWT in `app/api/auth/verify-otp/route.ts`. If omitted, the code falls back to `"secret"`.
- `SMTP_HOST`
  SMTP host for email delivery. Defaults to `localhost`.
- `SMTP_PORT`
  SMTP port. Defaults to `2525`.
- `SMTP_USER`
  SMTP username and sender identity.
- `SMTP_PASS`
  SMTP password.
- `AUTH_NOTIFY_EMAILS`
  Comma-separated list of recipients for OTP and audit emails.

There is currently no `.env.example` file in the repo.

## Security And Operational Notes

These are the most important caveats in the current implementation.

- The OTP gate is mostly client-side UX, not real route protection.
  `AuthGate` checks whether `auth_token` exists in `localStorage`, but the API routes do not validate that token before serving requests.
- The OTP email target is effectively fixed in the UI.
  `AuthGate` always requests an OTP for `admin@system.local`.
- OTPs are not sent to the email entered by a user.
  They are sent to `AUTH_NOTIFY_EMAILS`, while the requested email is only referenced inside the email content.
- All OTP/session/rate-limit state is in memory via `node-cache`.
  Restarting the server clears it. Multiple app instances would not share state.
- `NEXT_PUBLIC_CRYPTO_SECRET_KEY` is public by design.
  This is useful for compatibility with the upstream system, but it is not secret storage.
- `/api/proxy` can forward to arbitrary URLs.
  That is convenient for internal tooling, but it is a potential SSRF risk if the app is exposed broadly.
- `JWT_SECRET` falling back to `"secret"` is unsafe for any real deployment.
- Puppeteer capture requires a Node runtime with browser support and may be fragile in restricted hosting environments.

## Practical Mental Model

The simplest way to think about this app is:

- a small internal Next.js control panel
- one auth screen
- one operations dashboard
- one generic proxy to the real backend
- one Puppeteer route to extract encrypted credentials from an existing frontend

If we make future changes, the most likely hotspots are:

- auth hardening
- proxy restrictions
- Puppeteer stability
- better environment setup and deployment docs
- test coverage around the runner and auth flows
